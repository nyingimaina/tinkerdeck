## Decisions

- The request suggests hiding the big noise folders in the new file explorer by default, but that was never confirmed. When you open a project folder like this one (it has node_modules), what should the explorer show? → **Hide node_modules, .git, target and dist, with a 'show hidden' way to reach them** (telegram:6096790972)
- Tinkerdeck's editor stops feeling bolted on. ### Architect: design

Revision 1 of 3: the change adds a Files explorer beside the existing apps list. It is split into a small Rust core half and a small React window half, joined only by a typed boundary. The core half is a new standard-shaped module, src-tauri/src/features/explorer (with src-tauri/src/features/mod.rs), holding a plain, testable one-level directory lister and a Windows drive lister; two thin async #[tauri::command] shells run the filesystem work through tauri::async_runtime::spawn_blocking so the window thread never waits. The window half is a new feature in src/features/explorer (root.ts, useExplorer.ts, ExplorerPanel.tsx, ExplorerPanel.module.css) plus the typed boundary src/api/explorer.ts, which mirrors the two commands and is the only place the explorer calls invoke. The existing Sidebar gains one optional explorer slot (a Files section inside its expanded nav, never in the collapsed rail), so the app rows, Home row, rail and their tests stay as they are. App.tsx computes the root with a pure helper: app view uses the selected app's root; editor view uses ownerOf from src/state/editorGroups.ts, the same deepest-app-root lookup the tab groups use, and a Misc tab uses its file's parent folder. Up is temporary navigation that walks parents to the Windows drive list and is replaced by the automatic root whenever the view, selected app or active tab path changes; an app-rooted explorer offers no Up, so R4's top folder stays the app root. When no app root and no file path apply (home view, no tab, unsaved tab) the section shows a short hint and asks the core for nothing. Clicking a file calls useEditor.openPath, the existing editor_open_any path: it reuses/focuses an already-open entry by same_path, keeps images/PDFs on the existing preview-only handling and runs onOpened, which switches the main area to the editor view. Clicking a folder only expands or collapses it. The palette gains one unconditional 'Open file…' action that calls the same editor.openDialog the toolbar, Ctrl+O and empty-state button already use, so there is no second open path and those controls are untouched. Hidden names (node_modules, .git, target, dist) are filtered in the core and a Show hidden control turns them back on; an unreadable folder expands to a locked row with no thrown error. Design for scale: exactly one directory level is read per expand, nothing is recursive, cached, watched or polled, filtering/sorting/capping run once in the core, each level is capped at 1000 returned rows with a total/truncated marker, the per-root cache is capped at 100 levels with least-recently-used eviction, and row rendering is memoised. Low cost: no new npm package or crate, only an already-present windows-sys feature is switched on for GetLogicalDrives; one directory read per expand and one bounded readability probe per returned folder row; memory is the visible rows only; startup and CSP are unchanged. No new capability permission is needed (app-defined commands are not plugin commands); the dialog plugin already grants dialog:allow-open. The Windows desktop window has a 900x560 minimum, so the Files rows reuse the sidebar's existing 28-32px hit areas rather than adding mobile breakpoints (USR-001/002 are honoured by reuse, no new component library). Existing App suites gain a vi.mock for the new api module (the same pattern already used for api/tauri and api/editor). The version moves to 2.2.0 in package.json, package-lock.json, src-tauri/Cargo.toml, src-tauri/Cargo.lock and src-tauri/tauri.conf.json.
